# Networking — peer-to-peer rooms for up to four players

Players meet in a room identified by an 8-character code. Signaling goes over public Nostr relays, everything after that is direct WebRTC between the browsers. There is no game server: one player is the host and owns the room's shared facts. The session logic (`Session`) sits on a narrow `Transport` interface, so it runs unchanged against Trystero in the browser and an in-memory network in tests.

## How it works

### Layers

```
src/main.ts:connect / Session callbacks (games, players, pause menu)
        │
src/net/session.ts:Session        roles, roster, seats, rejoin, host migration
        │  typed messages, every payload validated by parse*()
src/net/protocol.ts               wire format + strict parsers
        │
src/net/transport.ts:Transport    send / on / onJoin / onLeave / leave
   ├── src/net/trystero.ts:trysteroTransport   (browser: Nostr signaling, then WebRTC)
   └── src/net/transport.ts:MemoryHub          (tests)
```

- `src/net/transport.ts:Transport` is the only thing `Session` knows about the network. *Why:* host election, seat assignment, migration and rejoin are the fragile parts of the game, and they must be testable without WebRTC (see [Shared clock and determinism](shared-clock-determinism.md), "Testing").
- `src/net/trystero.ts:trysteroTransport` wraps one Trystero room. Each message `type` becomes one Trystero action (`room.makeAction(type)`); a `to` argument turns into `{ target }`. Trystero keeps one handler per event, so the wrapper fans `onPeerJoin`/`onPeerLeave` out to a list (session and voice both listen). It also carries the voice streams (`addStream`; `src/net/trystero.ts:tuneVoice` raises bitrate and priority).
- `src/main.ts:connect` is the glue: roster to seats (`players.applyRoster`), host speed (`train`), blackouts, room options. `Session` stays free of scene code.

### Rooms and access

- The room code is the only access secret. `src/net/roomCode.ts:newRoomCode` draws `NET.codeLength` (8) symbols with `crypto.getRandomValues` from a 31-symbol alphabet (about 40 bits). *Why:* no `0/o`, `1/l/i`, so codes can be read aloud and typed by hand.
- Internal form is lowercase without a dash; `src/net/roomCode.ts:formatRoomCode` is display only (`ABCD-EFGH`). `src/net/roomCode.ts:normalizeRoomCode` accepts what people paste: any case, spaces, dashes, a full link or `#code`; it returns `null` for anything else.
- The code lives in the URL hash (`history.replaceState` in `src/main.ts`) and is also the Trystero password: `joinRoom({ appId: NET.appId, password: code }, code)`. *Why:* the relays then only see encrypted session descriptions, and a hash fragment is never sent to the static host. See the README section "Zugang, Datenschutz und Grenzen" for the user-facing wording.
- `NET.appId` (`'uknowhedoesntknow'`) namespaces the rooms on the relays, so other Trystero apps cannot collide with ours. Trystero picks its relays from a seeded shuffle of the appId, so every client uses the same five; some of them rate-limit.
- There is deliberately no pre-check whether a code is already in use. *Why:* with random codes a collision is about 1 in 850 billion, and if it happens anyway `hostClash` resolves it (below).

### Roles, roster, welcome

- The creator is `host` (`Session` constructor with `host = true`, seat 0); everyone else is `client` and sends `hello` with their `PersonState`, tab token and browser id. The host answers with `welcome` (`src/net/session.ts:welcomeMsg`): seed, `startMs`, current host clock, roster, train, blackout time, room options.
- A client's `welcome` event fires once, on the first welcome. Only then do seed and `startMs` overwrite the local `SharedClock` and the world can be built (`go` in `src/main.ts`). The joiner repeats `hello` every `NET.helloRetryMs` (`src/net/session.ts:tick`) until a host answers, because the host may still be connecting.
- The host owns the roster; every change is re-broadcast (`broadcastRoster`) as `roster` `{ e, r }` (the host's Host-Epoche and the entries, `src/net/protocol.ts:parseRosterMsg`), and clients mirror it (`applyRoster`). A client only accepts `roster`, `train`, `blackout`, `opts` and `pong` from `hostId`.
- Seats fill in `NET.seatOrder = [0, 2, 1, 3]`: on the hypertrain the first two players face each other instead of sitting side by side. A fifth joiner gets `full` (`NET.maxPlayers` = 4). `seatOrder` is only the seat fill order and the host-takeover rank; turn order in games comes from the real seat positions (`src/game/tableOrder.ts`, [Minigame framework](minigame-framework.md), "Rounds").
- Head poses (`pose`, `NET.poseHz` 20, rounded to 3 decimals by `src/net/protocol.ts:encodePose`) go peer to peer, not via the host. *Why:* they are cosmetic and a hop through the host would only add latency.
- Mouth levels (`lvl`, "Nur Mundbewegung") are sent by `src/audio/voice.ts:Voice` over the same transport, peer to peer: one byte 0..255, at most 12 per second per sender, only while above zero plus a closing 0, validated by `src/net/protocol.ts:parseLevel`. They replace the audio stream for players in that mode; details in [voice-audio.md](voice-audio.md), "Voice modes". *Why* not through the session or the host: cosmetic, like poses, and a host hop only adds delay.
- Minigame traffic uses one channel `mg` with `{ t, d }` (`src/net/session.ts:sendGame` / `onGame`). A message from a sender who is not in the roster *yet* is held (`holdGame`) for up to 10 s (`PENDING_GAME_MS`), at most 100 entries (`PENDING_GAME_MAX`, oldest dropped first), and delivered in arrival order when the roster grows (`flushPending`, called from `applyRoster`, after the host's `onHello` / rejoin and from `becomeHost`); entries that are older or still unknown are dropped. *Why:* a returning or new peer often sends its first game message before the roster that lists it has arrived, and dropping that message made reconnects lose cards and answers. One channel keeps the transport generic; games define their own message types. Games can also ask each other for lost data with `Recovery` (`mg:ask` / `mg:have`, [Minigame framework](minigame-framework.md), "Reconnect helpers").

### Untrusted peers

Every peer is just another browser. All wire data is validated by the strict `parse*` functions in `src/net/protocol.ts`: `parseState`, `parseLook`, `parseRoster`, `parseRosterMsg`, `parseEpoch` (a whole number, at most 1e9 either way, else the whole message is dropped), `parseWelcome`, `parseTrain`, `parseOpts`, `parsePose`, `parseName`, `parseLevel`. Numbers are range-checked, enums looked up, items only accepted in their own slot, missing fields fall back to defaults (`parseOpts`, `parseLook`), so older peers and saved profiles keep working. Only IDs and numbers travel, never geometry. When adding a message type, add a parser and use it at the receiving end; never cast `data`.

### Rejoin

People reload, lose WiFi or switch browsers, and a round must survive that.

- Everyone who leaves is remembered by **every** peer in `Session.gone` for `NET.rejoinMs` (30 min), together with seat, name and identity keys (`src/net/session.ts:remember`). *Why:* whoever becomes host later must be able to recognise returning players, so the memory cannot live on the host alone.
- Identity keys, in order of strength: tab token (`src/main.ts:tabToken`, `sessionStorage`, survives a reload, a new tab is a new person), browser id (`src/words/custom.ts:playerId`, `localStorage`, same browser in a new tab), then the player's name if exactly one gone player has it and nobody present does (`src/net/session.ts:findGone`). *Why:* another browser knows nothing of the old one, and in a room of friends the name is enough.
- Clients send the raw secrets only to the host in `hello`; the roster carries only short hashes (`src/net/protocol.ts:idHash`, `RosterEntry.keys`). *Why:* the hashes let any peer match a returning player after migration; the hash is not meant to be cryptographic, only to tell a few players apart.
- `src/net/session.ts:onHello` (host): a match gets its old seat back if free, and `ev.rejoin(oldId, newId)` fires; `src/main.ts` forwards it to every game's `rejoin()` so a running round continues under the new id. Seats of recently dropped players are held back from newcomers while other seats are free.
- `src/main.ts:rejoinCode` plus `src/main.ts:markInRoom` (`sessionStorage`): a reload inside a room with the same `#code` goes straight back in without the menu.
- `src/main.ts:absentBar` shows "`<Name>` ist getrennt, der Platz bleibt frei." with a button "Ohne `<Name>` weiterspielen" that calls each game's `drop(id)`. `NET.dropWaitMs` (30 s) is how long such a request waits for the host to notice the player is gone too.

### Host migration and split brain

- When the host leaves, `src/net/session.ts:onLeave` makes the remaining player with the best `seatOrder` rank (longest in the room) the new host. Everyone holds the same roster, so all peers reach the same decision without extra messages. The new host calls `becomeHost`, drops roster entries of peers that are not connected, and keeps seed, clock and train. Other clients just switch `hostId` and `clock.resetSamples()`. The rank (or a handover's successor hint) decides *who* takes over; the Host-Epoche below only decides between two hosts that exist at once.
- **Host-Epoche** (`Session.epoch`, carried in every `welcome` and `roster`). The room creator starts at 0. A peer that becomes host from epoch N (the last epoch a host announced to it, `known`) by a leave, the watchdog or "Raum selbst eröffnen" first claims **N − 1**, and **N + 2** as soon as another player of its roster shows it is really there: a `ping` (clients ping their host), a `hello` or a `state` (`Session.confirmed`); it then announces the new epoch by `welcome`. A handover target claims N + 2 at once (the old host asked it, so it is confirmed). Clients adopt the epoch of the host they follow from its welcome and roster; a client that elects someone else counts with N − 1 until the pick speaks. *Why the unconfirmed claim:* a peer that only lost its own connection sees everyone leave, often the host first while it still counts the others as connected, and makes itself host. Its claim must be weaker than the room's, or after the network comes back it would roll the room back to its stale state. A confirmation can only come from someone who really reaches it. *Why +2 / −1:* one number to compare: any confirmed new host (N + 2) beats a cut-off ex-host still at N, and an unconfirmed lone takeover (N − 1) loses against the room it left (still at N or above). **Jump bound and cap.** Epochs are whole numbers within ±`EPOCH_LIMIT` (1e9, `src/net/protocol.ts:parseEpoch`; anything else drops the whole message), and a host never computes one beyond it (`clampEpoch`). A claim from anyone but our own host (a welcome that would switch us, a clash partner's welcome or roster) is believed only if it is at most `EPOCH_JUMP_MAX` (64) above the epoch we know (`Session.plausible`); a host that meets a larger claim ignores it and stays. Welcomes and rosters from our own host are taken as they come. *Why:* a forged welcome with an epoch near the limit (any room member can send one) would otherwise win everywhere, and the real host that settled afterwards would need limit + 2, which every `parseEpoch` rejects: newcomers never welcomed, roster changes lost, while pings and the train still flow so no watchdog fires, until everybody reloads. *Why 64:* honest claims rise by 2 per host change (a seeded fuzz of splits, leaves and handovers never needed a jump above 14), so 64 still covers a peer that was cut off during dozens of host changes, while a forged claim near the limit is far beyond it. A forged claim just under the bound only raises the epoch a little; that is harmless.
- **Host watchdog (last resort).** A client that has heard nothing from its `hostId` for `NET.hostSilentMs` (6 s) treats it as gone (`Session.hostSilent`, from `tick`). Any accepted host message counts as a sign of life (pong, roster, train, blackout, opts, welcome), and following a new host restarts the count; it never runs on a host, nor before the first welcome (the join has its own hello retry). **Wake-up guard:** if `tick` itself has not run for more than `hostSilentMs / 2` (`lastTickAt`), the tick counts as a wake-up: the silence is counted from now and the watchdog skips this round. *Why:* a background or mobile tab is throttled to ticks seconds apart, and its pings (sent only from `tick`) went out late, so the missing pong says nothing about the host; without the guard such a client replaced a working host again and again. It runs the same election as for a host that left (`elect`: a fresh successor hint, else the best `seatOrder` rank), but among the peers it currently sees and without the silent one. If it elects itself it becomes host and announces it by `welcome`; otherwise it follows the pick and sends a `hello` to **every connected peer**, not only the pick (as the first join does). For `NET.hostSilentMs` after that hello (`probeUntil`) a welcome from a connected peer our roster does not list is taken as well, under the usual test (it lists us, a plausible epoch, and it beats our pick's claim). *Why everyone:* clients never answer a ping or a hello, so a client that follows a peer that is no host (stale roster, lost message) used to elect other clients one after the other (b, a, b, ...) and never the real host, which can rank last by seat and is not even in its roster; only a host answers a hello with a welcome. *Why this cannot pull anyone back:* the answer goes through the same epoch test as every welcome, so a stale ex-host (older epoch) is still refused, and only a better claim than the pick's moves us. Because it also fires when the host is a peer that is itself a client (it never answers pings), a client that is connected to the real host finds it within about two watchdog periods, whichever peers it picked before. (A race can still leave a room host-less for that long, never for good while players can reach a host.) Duplicate hosts it may create are settled by `hostClash`. *Why:* a room must never stay without a host, whatever interleaving of leaves, handovers and lost messages came before; the specific races are fixed where they arise, this catches the ones nobody thought of. Pings go every second (`pingSlowMs`), so a working host is heard well within the window; a slow link that still answers within 6 s is never replaced.
- A client that finds itself no longer in the host's roster (the host noticed a drop) re-sends `hello` with the same token, like a rejoin.
- `src/net/session.ts:hostClash`: two hosts exist when one was cut off and comes back, two peers elected themselves at once, or a handover's confirmation was late or lost. They exchange rosters on join; the higher Host-Epoche stays, on a tie the smaller id (`beats`). The loser becomes a client (`stepDown`, adopting the winner's epoch) and joins the winner like a returning player, so it keeps its seat. The winner answers by roster to the other host and by `welcome` to everyone, so the loser's followers switch too; it answers the same host at most once per 3 s (`CLASH_ANSWER_MS`, loop breaker). *Why epoch, then id:* both sides compare the same two numbers taken from the two messages, so they decide alike even in a partial mesh, and a host's epoch only rises while it stays host, so crossing messages can at worst make both answer once, never both give way. And the side that played on wins: a host cut off longer than leave detection comes back with an older epoch and loses, whatever the ids. *Why not room sizes* (an earlier rule): roster sizes differ between peers that see different parts of the mesh and between moments; two hosts then each judged themselves the winner (endless welcomes) or both gave way (nobody host). *Why not ids alone* (the rule before the epoch): after a real split, a cut-off ex-host with the smaller id won and rolled the room's progress back.
- **No rollback by welcome.** A client in a room takes a welcome only from a peer in its roster, and from anyone but its own host only if the welcome's claim beats its host's (`onWelcome`). A stale ex-host's welcome is refused, so nobody is pulled back to old state. From its own host a client takes roster and welcome as they come (it chose that host).
- `NET.orphanMs` (20 s): a joiner without any host sees "Noch niemand im Raum …" with a button "Raum selbst eröffnen" (`src/net/session.ts:takeOver`). The join is not cancelled, a host may still show up. *Why:* Nostr signaling alone can take about 10 s, and taking over too early would split the room in two.

### Host transfer ("Host übergeben")

The host can give the role to any other connected player on purpose (button in the Esc menu's player list, see [Menu, settings and input](menu-settings.md)). Same end state as a migration, but nobody has to leave.

- **Sequence.** `src/net/session.ts:handOver(id)` (host only) broadcasts `handover` with the target id and stays host, remembering `handing = { to, until }`. The target's `onHandover` accepts it only if it is a welcomed client, the sender is its `hostId`, and both are in its roster; it then runs `becomeHost(true, true)` (Host-Epoche N + 2, confirmed at once): drop roster entries it is not connected to, `status('host')`, broadcast a `welcome` to everyone, then the usual roster and train broadcast. Everyone, the old host included, takes the `welcome` (a client in a room takes it from any peer in its roster whose welcome lists it) and switches `hostId`, resetting clock samples and the ping schedule, so all peers ping the new host. A host that receives a welcome runs `hostClash`: the old host gives way to its handover target because of the target's higher epoch (`stepDown`, `status('client')`).
- **The welcome is the announcement.** Peers only take `roster`/`train`/`opts`/`blackout` from their current `hostId`. After the welcome (same channel, so in order) the roster and train that follow are already accepted. *Why the target is not simply told "you are host" by a message everybody applies:* the new host's roster could reach a peer before the old host's message did and be dropped. With the welcome, a peer follows whoever really became host.
- **Everyone else only notes the successor.** The other peers record the `handover` (`successor`, only from their current host, only for a player in their roster). If the old host leaves within `SUCCESSOR_MS` (15 s) of that, `onLeave` elects the noted player instead of the best `seatOrder` rank, so all peers agree even if the old host closes its tab before the new host's welcome has reached them. *Why:* without it, the peers that had not yet heard from the new host ran the rank election and made a second host (a clash the epochs would settle, but possibly against the target that already carries the round on). A handover that times out is called off by the old host sending `handover` naming itself; receivers drop the successor (otherwise a later leave of the old host would elect a target that never became host and the room would end up host-less).
- **At most one host that stays.** The old host stays host until the new host's welcome arrives, so normally the room always has a host. While `handing` is set it does not answer `hello` (the joiner repeats it every 2 s and then reaches the new host) and does not broadcast its roster. If nothing arrives within `NET.handoverWaitMs` (5 s) `tick` clears `handing`, sends the call-off and carries on as host. If the target leaves meanwhile, `onLeave` clears it too. A second `handOver` while one is open returns `false`.
- **Two hosts anyway heal themselves.** A late or lost confirmation, or the old host leaving at the wrong moment, can leave two hosts for a moment; `hostClash` (above) settles it. The target's epoch (N + 2) is higher than the old host's (N), so the target wins even when the old host timed out and carried on: there is no separate memory of who handed over to whom.
- **Welcomes are not trusted blindly.** A host that receives a welcome runs `hostClash` only if the welcome lists it and the sender is in its roster and connected; a client in a room takes a welcome only from a peer in its roster (or, right after its watchdog's hello, a connected peer outside it), and from a peer other than its host only with a better, plausible claim. A stranger's welcome changes nothing. (A peer that is in the room can still fake one, including a made-up epoch; it is a room of friends, and the `roster` message had the same property before. A forged welcome with a realistic epoch heals through the watchdog within a few seconds; one far above the epoch we know, up to the limit, is not believed at all, see the jump bound.)
- **The new host drops roster entries it is not connected to yet** (`becomeHost`, as in a leave takeover; here it can happen any time). Such a player, if they are really still there, sends `hello` again like any returning peer.
- **The host-takeover rank is otherwise unchanged.** When the new host later leaves, the best `NET.seatOrder` rank among the rest takes over, which may be the old host again.
- **What the old host loses:** in the short window before the welcome arrives, a client's `state` update (look or items) that reaches it is applied to its own roster but never forwarded, so it can be missing from the new host's roster until that client changes something again. Undo history stays behind as in any takeover. Games follow the takeover pattern ([Minigame framework](minigame-framework.md), "Absent players and rejoin/host takeover").
- **Known limit:** the clash fix tells the loser's followers by welcome, which only works for peers the winner has in its roster. After a real network split, followers of the losing host that the winner does not know are not moved (they send `hello` again only once they are dropped from a roster, or their watchdog moves them on once the loser stops answering pings, but only to a peer in their own roster); this was already so before host transfer. Also: until a freshly elected host is confirmed (usually its first ping, well under a second), its followers count with N − 1, so in that window a stale ex-host at N that is still in their roster could take them over by welcome; it then loses the clash against the confirmed host, which takes them back.
- Tests: `tests/hostTransfer.test.ts` (Session level: sweeps of the old host leaving at every network step for 3 and 4 players and every target, both leaving together in either order and seen in opposite order by different peers, late confirmations, asymmetric meshes, forged welcomes, the watchdog, its hello to everyone and its wake-up guard; forged epochs up to the limit and the jump bound, the cap clamp, honest jumps over ten handovers; a seeded mini-fuzz of splits, heals, leaves and handovers; real network splits healing with the room winning in both id orders, for a cut-off host and a cut-off client; epoch ties; plus a "Wer bin ich?" round that continues under the new host). `MemoryHub.disconnect(id, true)` lets a leaver's earlier messages arrive first.

### Failure handling in the UI

- `src/main.ts:showProblem` / `src/main.ts:hideProblem`: one calm notice in the middle for problems, with a hint what to do. The `offline` event shows "Keine Internetverbindung. Sobald sie zurück ist, verbindet sich der Raum von selbst neu."; `online` hides it.
- Trystero join errors only go to `console.warn` (the `onError` callback passed in `src/main.ts`).

### Known limitations

- No STUN `iceServers` are configured. Same-machine Firefox to Firefox can fail ICE; online and with Chrome it works.
- P2P shows players each other's public IP; unavoidable (README, "Zugang, Datenschutz und Grenzen").
- Trystero's fixed relay set means a rate-limiting relay can slow the first connection.

## Using it

Menu: "create" makes a code and opens the room; "join" takes a pasted code or link (`src/ui/menu.ts`). While connecting, the menu shows "Verbinde mit Raum …". The pause menu lists players, role and round-trip time (`pause.setRoom` in `connect`); the host also gets a "Host übergeben" button on every other player's row. A full room shows "Der Raum ist voll (4 von 4).".

For multi-device development with `npm run dev:lan`, HTTPS with a throwaway certificate is required (Trystero needs WebCrypto, a secure context), and the host names the dev server accepts come from the environment variable `UKHDK_ALLOWED_HOSTS` (comma-separated, read through Vite's `loadEnv`, so a shell variable or a git-ignored `.env.local` works; unset means Vite's default host check), for example `UKHDK_ALLOWED_HOSTS=<your-host-name> npm run dev:lan`. Details in [debug-build.md](debug-build.md).

## Options

| Config key (`NET` in `src/config.ts`) | Default | Meaning |
| --- | --- | --- |
| `appId` | `'uknowhedoesntknow'` | Relay namespace |
| `maxPlayers` | 4 | Seats |
| `seatOrder` | `[0, 2, 1, 3]` | Seat fill order and host-takeover rank (not the turn order) |
| `codeLength` | 8 | Room code symbols |
| `poseHz` / `poseKeepAliveMs` / `poseEpsilon` | 20 / 1000 / 0.002 | Head pose rate, keep-alive, minimum change |
| `remoteRate` | 18 | Smoothing of remote heads |
| `rejoinMs` | 30 min | How long a dropped player's seat is remembered |
| `dropWaitMs` | 30 s | Wait for the host before "play on without them" |
| `helloRetryMs` | 2 s | Joiner repeats hello |
| `pingFastMs` / `pingFastCount` / `pingSlowMs` | 250 / 8 / 1000 | Clock ping cadence |
| `orphanMs` | 20 s | Without a host: offer to reopen the room |
| `hostSilentMs` | 6 s | A client that heard nothing from its host this long elects a new one (watchdog); a tick after a gap of more than half of it only restarts the count |
| `handoverWaitMs` | 5 s | The host who handed over waits this long for the new host's welcome, then stays host |
